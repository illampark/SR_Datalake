# SR DataLake — 2026-09-08 작업 로그

## 오전 세션 — 프로덕션 서비스 점검 · HTTPS 진입점 장애 복구

**코드 변경 없음.** 운영 서버 상태 점검 중 고객 HTTPS 진입점 다운을 발견해 복구했다.
서버 조회는 전부 읽기 전용으로 했고, 복구 명령(sudo)은 접근 권한 문제로 illam 이 직접 실행했다.

### 장애 — 고객용 HTTPS 진입점 약 3주 다운

**증상**: 외부 `https://106.254.248.74:51404` 연결 거부(TCP RST). 앱 컨테이너는 전부
healthy 인데 고객이 접속할 수 없는 상태.

**원인 체인** (조회로 특정):
- 프로덕션 호스트가 **2026-08-18 07:44 UTC 에 재부팅**됐다(uptime 20일 17시간).
- 컨테이너 5개는 `restart: always` 라 전부 자동 복구됐다(restarts=0, StartedAt 08-18).
- 그러나 **nginx.service 가 `disabled`** 상태여서 부팅 시 기동하지 않았다.
- nginx 가 유일한 TLS 종단이자 5001 로의 리버스 프록시(`/etc/nginx/sites-enabled/sdl`,
  `listen 443 ssl http2` → `proxy_pass http://127.0.0.1:5001`)이므로, 재부팅 순간부터
  외부 진입로가 끊겼다.
- 앱은 평문 5001 에 정상(302 / login 200)이었으나 `SESSION_COOKIE_SECURE=true` 라
  HTTP 우회 로그인도 불가.

**증거**:
- 재부팅 전 마지막 고객 로그인 `dd3@daeduck.com` 2026-08-13 01:38, 이후 로그인 0건.
- nginx: `systemctl is-enabled` = disabled / `is-active` = inactive(dead).
- 호스트에 443 리스너 없음. compose 에 443 포워딩·프록시 서비스·인증서 마운트 없음
  (nginx 는 호스트 서비스이지 컨테이너가 아니다).

**복구** (illam 이 sudo 로 직접 실행):
```
sudo nginx -t
sudo systemctl enable --now nginx
```
`enable` 이 핵심 — disabled 가 원인이었으므로 이걸 붙여야 재부팅 재발을 막는다.

### 발견 — 접근·자격증명 정정

- **프로덕션은 접근 가능하다.** 지난 HANDOFF 의 "프로덕션 접근 불가" 는 오류였다.
  프로젝트 폴더의 `id_ed25519`(스테이징·DGX용)만 시도했고 **맥 홈의
  `~/.ssh/id_ed25519` 키**를 시도하지 않았다. 이 키로 접속된다.
  SSH 는 **키 인증만** 동작하고 비밀번호 인증은 막혀 있다.
- **sudo 비밀번호가 문서 세 곳과 다르다.** 실제 값은 첫 글자 대문자 + `#` 구분자
  형식이다(값 자체는 이 리포에 적지 않는다 — 비밀번호 관리자에 둔다).
  로컬 `server_info.txt`·스테이징 `server_info.md` 양쪽에 낡은 값(`blunex@0429`)이
  적혀 있어 거부됐다. → 보안 정리 과제(server_info 갱신)에 묶인다.
- **자동화 제약**: 자동 모드 분류기가 비밀번호를 넣어 sudo 를 실행하는 명령을
  차단한다. 운영 서버의 권한 상승 작업은 illam 이 직접 실행해야 한다.

### 운영 권고

- **다른 호스트 서비스도 enabled 인지 점검 필요.** 이번은 nginx 만 disabled 였으나,
  재부팅 생존이 compose(restart:always)에만 의존하고 호스트 서비스는 개별 관리라
  같은 함정이 반복될 수 있다. mosquitto·minio 등은 컨테이너라 무관하지만, 향후
  호스트에 서비스를 추가하면 enable 을 습관화한다.
- **외부 진입점 감시 부재.** 3주간 다운을 인지하지 못했다. `:51404/login` 200
  확인을 verify-handoff 나 별도 헬스체크에 추가하면 조기 발견이 가능하다.
