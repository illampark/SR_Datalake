### DB 커넥터 → 내부 sink 매핑 구조 (조사 결과)

소스 테이블에서 타겟 테이블을 **유도하는 규칙은 없다.** 태그명으로 MQTT 토픽을
만들어 라우팅하고, 타겟 테이블은 sink 스텝에 사람이 적어 넣는다.

```
config.tables[].name
  → db_tag(connector_id, table_name, tag_name)        ← 테이블명을 태그명으로 번역
  → sdl/raw/db/{connector_id}/{tag_name}              ← 행 1건 = 메시지 1건
  → pipeline_binding.tag_filter                       ← 구독 토픽의 마지막 세그먼트
  → pipeline_step.config.tableName                    ← 순수 수동 지정
```

- **발행**: `backend/routes/collector_db.py` `/callback`. Benthos 는 폴링 트리거만
  던지고 실제 조회는 이 라우트가 한다. `matched_tags = [t for t in tags if
  t.table_name == tbl_name]` 로 태그를 찾고, 없으면 테이블명을 태그로 쓴다.
- **구독**: `backend/services/pipeline_engine.py:182-193`.
  `topic = f"sdl/raw/{type}/{id}/{tag_filter}"` 로 조립한다. `tag_filter` 가 `*` 이면
  `#` 와일드카드.
- **싱크**: `backend/services/pipeline_modules.py:936`
  `table_name = config.get("tableName") or "pipeline_data"`.

### 발견

- **`pipeline.input_topic` 컬럼은 실제로 쓰이지 않는다.** 9개 파이프라인 전부
  `sdl/raw/#` 로 같은 값이 들어 있지만, 구독은 `pipeline_binding.tag_filter` 로
  조립한 정확한 토픽에 건다. 메시지 본문을 파싱해 분기하는 로직도 없다 —
  **브로커의 토픽 매칭이 곧 분배기다.** DB 컬럼만 보고 "전부 같은 토픽을 듣는다" 고
  읽으면 틀린다.
- **`data_lineage.destination_target` 이 sink 테이블이 아니라 MQTT 출력 토픽이다.**
  `pipeline_engine.py:408` 이 `destination_target=output_topic` 으로 기록하고,
  싱크 실행은 그 뒤에 일어나 계보에 반영되지 않는다. 실제 `생산로트` 계보 행은
  `mqtt / sdl/processed/6/생산로트` 이며 `mes_lot` 은 어디에도 없다.
  → **계보 화면으로는 "데이터가 어느 테이블에 쌓였는가" 를 답할 수 없다.**
  게다가 `생산로트` 계보는 08-10 12:34 의 1건(100행)뿐이라 이후 적재분이 남지 않았다.
- **`id` 컬럼 충돌은 설정으로 우회 중이지 코드가 고쳐진 게 아니다.** sink 가
  `id SERIAL PRIMARY KEY` 를 강제하므로 소스에 `id` 가 있으면 실패한다. FDC 두
  테이블이 `customSql` 에서 `SELECT id AS src_id` 별칭으로 피해 가고 있다.
  같은 문제를 다른 소스에서 다시 만나면 또 별칭을 붙여야 한다(decisions/0001).
- **한글 태그명이 MQTT 토픽 세그먼트다.** `db_tag.tag_name` 과
  `pipeline_binding.tag_filter` 가 문자열로 이중 관리되며 **참조 무결성이 없다.**
  태그명을 바꾸면 구독 토픽이 어긋나 조용히 수집이 끊긴다.
- **한 테이블에 태그를 여러 개 달면 행이 복제된다.** `for tag in matched_tags` 가
  태그마다 발행하므로 같은 소스 행이 태그 수만큼 다른 토픽으로 나간다.
  의도한 팬아웃이면 정상이지만 실수로 중복 등록하면 중복 적재가 된다.
